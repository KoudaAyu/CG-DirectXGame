## 1. なぜ「アプリケーション層（ゲームプレイ実装）」が合否を分けるのか

セガをはじめとする大手ゲーム開発会社の技術面接・書類選考において、自作ゲームエンジンを作っていることは**大きなプラス（基礎力・ハードウェア理解の証明）**になります。  
しかし、同時に審査官（現役シニアプログラマ）は必ず次の視点を持っています。

> **「エンジンが書けるのはわかった。で、この人は面白いゲームを作れるプログラマなのか？」**  
> **「ゲーム仕様の変更に耐えうる柔軟なゲームロジック設計ができるか？」**  
> **「プレイヤーへのフィードバック（手触り、情報提示、演出）を大切にしているか？」**

現在の『Escape from Duckov』はエンジン基盤（DirectX12、衝突判定、JSONリロード、パーティクル）が強固に整いました。  
次に行うべきは、**「ゲームプログラマとしての腕前を見せつけるアプリケーション層の肉付け」**です。

---

## 2. 現状のコードベース分析と課題

| 項目 | 現状の実装 | 面接官から見た懸念点 |
| :--- | :--- | :--- |
| **敵管理** (`GamePlayScene`) | `enemy_` と `movingEnemy_` の2体個別ポインタ | 「敵を増やしたり、ウェーブ制にするときどうするの？設計がスケールしないのでは？」 |
| **ゲーム展開（緩急）** | 標的破壊 → 脱出地点へ移動するだけの単一フェーズ | 「ゲームプレイの起承転結（ピンチとチャンス）がなく、飽きやすい」 |
| **敵AIのフィードバック** | `Patrol / Investigate / Chase` のステートはあるが、見た目の伝達が薄い | 「AIが賢く作られていても、プレイヤーに伝わっていなければ存在しないのと同じ」 |
| **戦闘の選択肢** | 単一の射撃仕様（AK-74M固定） | 「立ち回りの工夫（遠距離・近距離の使い分け）が生まれにくい」 |
| **脱出の報酬** | ルートアイテムを拾ってもクリア時の達成感・精算が薄い | 「エクストラクションシューターの最大の特徴である『欲張って死ぬリスク＆リワード』が弱い」 |

## 3. 優先度別：今すぐ実装すべき4つのアプリケーション機能

### 【優先度★★★】① 敵の動的配列管理と「増援フェーズ（Alert Phase）」の実装
#### 目的
固定ポインタ（2体）を脱却し、拡張性のあるオブジェクト指向設計を示す。さらにゲーム後半の緊張感を跳ね上げる。

#### 実装方針
- `GamePlayScene.h` の個別ポインタをコンテナ化：
  ```cpp
  // 変更前
  std::unique_ptr<Enemy> enemy_;
  std::unique_ptr<Enemy> movingEnemy_;

  // 変更後
  std::vector<std::unique_ptr<Enemy>> enemies_;
  ```
- **脱出阻止フェーズ（増援スポーン）の追加**:
  - 全標的（Target）を破壊した瞬間、サイレン音/パーティクル演出とともに**警戒フェーズ**へ移行。
  - 脱出地点（ExitZone）の周辺またはマップ端から、新たに追跡特化の敵AIを2〜3体追加スポーンさせる。
  - 「クリア直前が一番危ない」というタルコフ系特有のヒリつきを生み出す。

---

### 【優先度★★★】② 敵AIの「警戒・思考状態」可視化インジケータ
#### 目的
「プレイヤーに情報をわかりやすく伝える力（UI/UXとゲームロジックの連携）」をアピールする。

#### 実装方針
- `Enemy` の頭上に、現在の `AIState` に応じたビルボード/2Dマーカーを表示：
  - **Patrol (巡回)**: 表示なし、または穏やかな白色アイコン
  - **Investigate (索敵・音の調査)**: 頭上に黄色い **「？」** マーカー表示
  - **Chase / Alert (発見・追跡)**: 頭上に赤い **「！」** マーカー＋警告音・小規模パーティクル
- **アピールポイント**:
  - 「ステートパターンの状態遷移を、グラフィック層と直結させてプレイヤーに認知させている」ことを面接で自信を持って話せる。

---

### 【優先度★★☆】③ 武器切り替えシステム（アサルトライフル vs ショットガン/SMG）
#### 目的
プレイヤーの意思決定（タクティカル要素）を増やし、武器パラメータのデータ駆動設計を示す。

#### 実装方針
- `F` キーまたは `1/2` キーで主武装と副武装を切り替え可能にする。
- **AK-74M（初期武器）**:
  - 中距離向け、連射速度普通、拡散度低め、単発威力高
- **Shotgun（新規追加: 散弾） または MP5K（高レートSMG）**:
  - 近距離向け、1回の射撃で複数ペレットを扇状に発射、至近距離で大ダメージ
- **アピールポイント**:
  - 「単なる弾丸生成ではなく、拡散角（Spread Angle）や弾数、射程距離をパラメータ化し、武器クラスまたはデータ駆動で管理している」点をアピールできる。

---

### 【優先度★★☆】④ リスク＆リワードの明確化（脱出リザルト精算画面）
#### 目的
「ゲームデザイン」を理解していることを提示する。

#### 実装方針
- `ClearScene` に、持ち帰ったアイテム一覧とスコアを表示：
  - 拾った物資の合計価値（ルーブル換算）
  - 倒した敵の数（Killボーナス）
  - 残り時間 / 被ダメージ量によるランク判定（S / A / B / C）
- **アピールポイント**:
  - 「プレイヤーが『もう1部屋探索して物資を拾うか、安全に今すぐ脱出するか』のジレンマを感じる仕組みをプログラミングした」と説明可能。

## 4. やらなくていいこと（工数の罠・避けるべきこと）

限られた制作期間の中で、以下の項目に時間を使うのは**悪手**です。

1. **× エンジン機能の大規模追加**
   - 既に十分高機能（Dx12、衝突判定、JSONリロード、パーティクル等）。これ以上DirectXの機能（レイトレ等）を足すより、ゲームを面白くする方が100倍評価されます。
2. **× 巨大なマップや複雑な地形**
   - マップが広くなると移動時間が退屈になり、審査員がプレイした時にダレます。ワン画面＋アルファ程度のコンパクトな戦闘密度が最適です。
3. **× リアルな3Dモデリングやアニメーションの自作**
   - プログラマ志望の選考です。Blenderで何週間もかける必要はありません。プリミティブや既存モデルの組み合わせでも、「動きの緩急」「ヒットストップ」「カメラシェイク」などの**コードによる演出**があれば十分高評価です。

> **【技術的アピール】**  
> 自作DirectX12ゲームエンジン上に構築したトップダウン・タクティカルシューター。  
> 
> - **エンジン層**: JSONホットリロードによるイテレーション向上、疎結合なSceneContext、効率的なOBB/AABB衝突判定システムを実装。
